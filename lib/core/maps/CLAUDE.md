### Trip Route Segments, Pluggable Map & Premium Feature Flags (Stage 20)

**Migration:** `docs/supabase_migrations/stage21_trip_segments.sql` (numbered 21 to match the file's own stage — `stage20_push_tokens_conflict_fix.sql` already existed).
Must be run in Supabase SQL editor before deploying the corresponding app build.

#### What it does

Lets a trip be planned as an ordered sequence of transport legs — e.g. Flight Munich→Bangkok, Flight Bangkok→Chiang Mai, Motorcycle Chiang Mai→Pai, Motorcycle Pai→Chiang Mai, Flight Chiang Mai→Bangkok, Flight Bangkok→Munich — rendered as a map with per-mode icons. This is additive: it does **not** touch the existing flat `items` (`ItineraryItem`) list, which has no ordering or origin/destination concept to retrofit.

#### Database schema additions

**`public.trip_segments`** — one row per leg: `itinerary_id` (FK cascade), `order_index int`, `transport_mode text` (`check in ('flight','train','bus','car','motorcycle','ferry','walk','other')`), `origin_name/lat/lng`, `destination_name/lat/lng`, `departure_time`/`arrival_time timestamptz`, `notes`. Origin/destination are **denormalised full waypoints on every row**, not a shared/linked waypoint id — editing one segment's destination does not retroactively update the next segment's origin; continuity between legs is a UI convenience at creation time only ("Continue trip from here", see below), not an enforced invariant. No unique constraint on `(itinerary_id, order_index)` — every add/delete/reorder mutation renumbers the whole list 0..n-1 and writes it back as one batched `upsert`, which is simpler and self-healing at the realistic scale (a handful to a few dozen segments per trip) rather than doing incremental index-shifting.

RLS follows the `stage13_fix_member_jsonb_all_tables.sql` pattern (`EXISTS + jsonb_array_elements`, checking both `user_id` and `userId`), with write access open to any **editor/owner member** — segments are shared trip content like the itinerary row itself, not creator-only content like an expense.

**`public.profile_status`** — an **append-only history log** of premium grants/expirations (`user_id`, `status` [`premium`|`normal`], `reason`, `expires_at`, `created_at`), not a flat `is_premium`/`premium_until` column on `profiles`. Mirrors the existing `username_history`/`profile_change_log` (Stage 16) pattern: "is this user premium right now" is always the single most recent row for that user, checked against `expires_at`, so a look at the table six months from now always has a reason attached instead of an unexplained date. Owner-only read RLS; rows are written only by `handle_new_user` (grants a signup trial) and `close_expired_premium_status()` (both `SECURITY DEFINER`), or directly by the service role for goodwill/subscription grants.

**`public.feature_flags`** — small, admin-controlled table (`feature_key` PK, `requires_premium bool`, `free_until timestamptz`, `description`) gating premium features generically, not just Google Maps. Read-all RLS, no write policy (service role only). Seeded with `google_maps` at `requires_premium = false` — free for everyone today; flipping it to `true` later gates it for non-premium users, and `free_until` grants a temporary grace-period override without touching `requires_premium`.

**`public.app_config`** — generic key/value table for small tunables, first used for `trial_duration_days` (default `14`) so the signup trial length is an ops change (`UPDATE` one row), not a deploy. Same read-all/service-role-write pattern as `feature_flags`.

#### RPCs / functions

- **`close_expired_premium_status()`** — `SECURITY DEFINER`, no params (uses `auth.uid()` internally). Lazily inserts the terminating `'normal'` row when the caller's latest `profile_status` row is an expired `'premium'` grant. Called by the client right before it reads its own status, so the log self-heals with no cron/scheduled job needed; idempotent once the terminating row exists.
- **`handle_new_user()`** — reissued to also insert a `'premium'` / `"{trial_duration_days}-day trial on signup"` row with `expires_at = now() + trial_duration_days` (read from `app_config`) for every new profile.
- Existing users are backfilled with the same trial grant (idempotent — only inserts where no `profile_status` row exists yet).

#### Flutter layer

- **Domain:** `lib/features/itinerary/domain/entities/` — `transport_mode.dart`, `waypoint.dart`, `trip_segment.dart`; `trip_segment_repository.dart`; usecases for add/update/delete/reorder (no "fetch" usecase — the stream goes straight from repository to provider, matching the `expense_split` convention).
- **Data:** `trip_segment_model.dart` (manual `fromJson`/`toJson`, no code-gen — matches every other feature model in this codebase), `trip_segment_remote_datasource.dart`, `trip_segment_repository_impl.dart`.
- **Map abstraction** (`lib/core/maps/`): `kumo_map_provider.dart` — `KumoMapProvider` enum (`openStreetMap` | `googleMaps`) + `MapProviderNotifier`, cloned from `theme_provider.dart`'s exact StateNotifier/SharedPreferences pattern (pref key `kumo_map_provider`, default `openStreetMap`). `route_map_view.dart` — public `RouteMapView` widget dispatching to a private `_OsmRouteMap` (`flutter_map` + `latlong2`) or `_GoogleRouteMap` (`google_maps_flutter`); callers never touch a specific map package. Tap targets are markers only — `flutter_map`'s `PolylineLayer` has no hit-testing, so tapping the connecting line itself isn't supported.
- **Curved to-and-fro legs** (`lib/core/maps/route_curve.dart`): a round-trip pair (e.g. Chiang Mai → Pai then Pai → Chiang Mai) drawn as two straight lines lands exactly on top of itself. `hasReverseLeg` detects when some other segment in the trip covers the same two waypoints in the opposite direction (waypoints compared with a ~5-6 km epsilon, since independently geocoding "the same" city twice doesn't always return bit-identical coordinates); `curvedPath` then renders that segment as a quadratic-Bezier arc instead of a straight line, and leaves everything else straight. The bow direction is always "left of this segment's own travel direction," computed independently per segment — since a return leg's direction vector is the outbound's negated, "left of a negated vector" mirrors to the opposite side automatically, so the two directions of a to-and-fro pair separate visually with no explicit outbound/return tracking needed. Pulled into its own file specifically so this geometry has real unit tests (`test/core/maps/route_curve_test.dart`) rather than only being exercisable through a mounted map widget.
- **Tyre-tread route textures**: `singleTread` (motorcycle) and `doubleTread` (car/bus) no longer draw a plain line + generic tick/chevron — the tick shapes are the **literal `<path>`/`<rect>` coordinates** from `assets/icons/motorcycle_tyre_tread.svg`'s and `assets/icons/car_tyre_tread.svg`'s repeating pattern modules (every sub-shape, including the moto blocks' original cubic-bezier curves via `Path.cubicTo`, and the car module's centre traction strip — not a simplified stand-in), recentred on each SVG's own pattern-tile midpoint and rescaled (moto ×0.18, car ×0.12). They're hand-ported rather than `flutter_svg`-rendered because these need to be tiled and rotated per sample point along a curving, zoom-independent route line, which an embedded static SVG picture can't do — an earlier pass at this drew invented "shoulder block + chevron" placeholder shapes instead of actually porting the SVGs' geometry, which is why it looked off; this is the corrected literal port. `_drawMotoTreadBlocks`/`_drawCarTreadBlocks` in `route_line_painter.dart` are the OSM engine's versions (local frame: `+y` = travel direction, matching `_drawFootsteps`); the `RouteTexture.singleTread`/`doubleTread` cases in `route_marker_bitmaps.dart`'s `textureTickBitmap` are the same coordinates re-derived for the Google engine's bitmap-tick convention (`-y` = travel direction, i.e. "up" in the bitmap — see the Python snippets used to compute both engines' coordinate sets from the same source scale/recentring, so they don't drift apart by hand-transcription error). For `doubleTread` specifically, the full car module (all 8 shoulder/chevron blocks + both centre-strip segments) is applied **per wheel track** rather than a simplified single shape once across the centreline (the "double trace" look) — OSM draws it twice at `±railOffset` (`7`, sized to the ported module's ~10.8px width) from the path; Google samples the same tick bitmap along both `offsetPath(geoPath, ±halfGap)` rails instead of the centreline (see the `texture == RouteTexture.doubleTread` branch in `_GoogleRouteMapState._buildMap`'s tick-placement loop). The `±halfGap` fraction (`_doubleTreadHalfGapFraction`, `0.0315` of the segment's own path length — `0.018` scaled by the same `7/4` ratio as the OSM rail-offset increase) is shared between that loop and `_addPolylinesForSegment`'s rail polylines so the tick blocks can't drift off the rails they're meant to sit on.
  - **Tick density, all four ticked textures**: a fixed tick *count* over the whole segment spreads the same handful of ticks thin on a long or heavily-zoomed segment. `_carTreadTickCount`/`_motoTreadTickCount`/`_footstepsTickCount`/`_trainTrackTickCount` in `route_line_painter.dart` fix this for the OSM engine — every one of `paintRouteTexture`'s non-`dashedLine` cases now spaces its own ticks at a constant **pixel** interval instead of a shared fixed count (`_carTreadPeriodPx = 3.6`, `_motoTreadPeriodPx = 6`, `_footstepsPeriodPx = 9`, `_trainTrackPeriodPx = 10` — the tread periods derived from each module's own along-travel extent to read near-continuous like the source SVGs tile; the footsteps/sleeper periods chosen directly for a natural gait/railway-tie look rather than derived from a bounding box). Because every case now computes its own samples, `paintRouteTexture` no longer computes a shared `samples`/`tickCount` at the top the way it originally did. The Google engine has no equivalent (it samples in geographic coordinates, where "constant pixel spacing" isn't meaningful without live zoom) — `tickCountForTexture` in `route_texture.dart` still exists and is called **only** by the Google engine now, with every value raised from each texture's original fixed count (`footsteps` `14`→`32`, `singleTread` `18`→`40`, `doubleTread` `10`→`24`→`60` over two rounds of tuning, `trainTrack` `9`→`21`) to read closer to the OSM engine's new density.
  - **Tread width vs. rail gauge (`doubleTread` only)**: the ported car module (`_drawCarTreadBlocks`, and the matching Google bitmap case) is squeezed to 70% width on its cross-axis (`x`) only, `y` (along-travel) untouched — narrower blocks sitting on the *same* rails. This is deliberately not a uniform scale-down: `railOffset`/`halfGap` (the rail gauge — how far apart the two wheel tracks themselves sit) is untouched by this squeeze, so narrowing the tread never pulls the two tracks closer together.
- **Mode-icon direction indicator**: the mid-route mode icon (`_ModeIconMarker` in `route_map_view.dart`, mirrored for the Google engine via `modeIconBitmap`/`directionArrowBitmap` in `route_marker_bitmaps.dart`) is deliberately **never rotated** — most Material glyphs used here (`directions_walk`, `directions_bus`, `directions_boat`, `flight`) bake in a real "up" (a head, a roof, a fuselage) as well as a facing direction, so rotating the whole glyph to match a segment's bearing made it render upside-down for southbound-ish segments. Direction of travel is instead shown by a small triangular arrow badge that orbits the (always-upright) icon at the segment's bearing — for OSM this is `_DirectionArrow`, a `CustomPaint` positioned via `Align(topCenter)` inside a `Transform.rotate`d box centred on the icon; for Google Maps it's a second marker at the same lat/lng using `directionArrowBitmap` (drawn near the top edge of a canvas centred on `anchor: (0.5, 0.5)`, so `Marker.rotation` sweeps it around the icon instead of spinning it in place). A plain triangle has no "correct" orientation, so it reads fine at any rotation, unlike the mode glyph.
- **Geocoding** (`lib/core/geocoding/`): `geocoding_service.dart` abstract interface + `nominatim_geocoding_service.dart`, a free OSM Nominatim-based implementation used for location search regardless of which map provider is active (so typing a city name never needs a Google key). Sets a descriptive `User-Agent` and throttles to Nominatim's 1 req/sec policy — debounce alone doesn't guarantee that for a fast typer.
- **Premium** (`lib/core/premium/`): `profile_status.dart` (entity, `isCurrentlyPremium` getter), `profile_status_datasource.dart` (calls `close_expired_premium_status()` then reads the latest row), `premium_feature.dart` (`PremiumFeature`, `PremiumFeatureKeys.googleMaps`), `premium_datasource.dart` (fetches all `feature_flags`), `premium_providers.dart` (`featureFlagsProvider`, `currentProfileStatusProvider`, `isPremiumUserProvider`, `canUseFeatureProvider` family — a feature with no matching row defaults to *allowed*, since missing data should never lock users out of something meant to ship free).
- **Presentation:** new "Route" tab in `itinerary_detail_page.dart` (`_RouteTab`) showing `RouteMapView` + an ordered `SegmentCard` list. Tapping a segment card or its destination marker opens a unified **segment actions sheet** (`segment_actions_sheet.dart`): *Continue trip from here* (prefills the next leg's origin with this segment's destination, inserts after it, renumbers), *Edit*, *Delete*. `add_edit_trip_segment_page.dart` mirrors `add_edit_item_page.dart`'s shape, with a `TransportMode` icon-chip picker and `location_search_sheet.dart` (adapted from `edit_profile_page.dart`'s `_LookupSheet`, swapping its static-list filter for a debounced, network-backed `GeocodingService.search`). New router entries `/trip/:id/segment` (add, optional `extra: TripSegment` for the "continue from" prefill) and `/trip/:id/segment/:segmentId` (edit), mirroring the existing `item`/`item/:itemId` pair.
- **Settings:** "Map Provider" tile + picker sheet in `profile_page.dart` (`_MapProviderPickerSheet`, cloned from `_ThemePickerSheet`). The Google Maps option shows a lock icon and an upsell snackbar instead of switching when `canUseFeatureProvider(PremiumFeatureKeys.googleMaps)` is false.

#### Google Maps native key wiring

A scalar API key can't be gitignored as a whole file the way the Firebase configs were, so it's indirected:
- **Android:** gitignored `android/app/src/main/res/values/google_maps_api.xml` defines a `google_maps_key` string resource; the committed `AndroidManifest.xml` references it via `<meta-data android:name="com.google.android.geo.API_KEY" android:value="@string/google_maps_key"/>`. The `.example` template lives at `android/app/google_maps_api.xml.example` — **not** inside `res/values/` — because Android's resource merger scans every file under `res/values/` and requires it to end in `.xml`; a `*.xml.example` placeholder there breaks the build (`Resource and asset merger: The file name must end with .xml`, hit for real during Stage 20's run-skill setup).
- **iOS:** gitignored `ios/Runner/Secrets.xcconfig` (+ `.example`) defines `GOOGLE_MAPS_API_KEY`, `#include`d from `Debug.xcconfig`/`Release.xcconfig`, surfaced to `Info.plist` as `GMSApiKey`, read in `AppDelegate.swift` via `GMSServices.provideAPIKey(...)`.
- No Android/iOS permission changes were needed — `INTERNET` is already merged in transitively (Firebase Messaging), and both tile/geocoding hosts are HTTPS.
- The premium gate above is client-side only and doesn't stop a patched client from reaching the Google Maps code path; real protection is restricting the Maps API key in Google Cloud Console to this app's Android package+SHA-1 / iOS bundle ID, independent of the `feature_flags` system.

#### Key design decisions

- **`profile_status` as an audit log, not a column**, for the same reason `username_history`/`profile_change_log` exist — a mutable "current state" field can't explain itself later; an event log always can.
- **Client calls `close_expired_premium_status()` lazily** rather than running a scheduled job, because this project has no cron/scheduled-function precedent yet; the function is cheap and idempotent, so calling it on every status read is simpler than standing up new infrastructure for it.
- **`material_design_icons_flutter` (an unused pubspec dependency since Stage 19) turned out to be incompatible with the current Flutter SDK** — its pinned version subclasses `IconData`, which is now a `final class`. Transport-mode icons use built-in `Icons.*` instead; the dependency itself has since been removed from `pubspec.yaml` since nothing used it.

#### Not yet implemented — org/sub-org premium inheritance

Raised during Stage 20 planning: rather than a single global `trial_duration_days` value in `app_config`, premium defaults (trial length, feature-flag overrides) could eventually be inherited from a global default and overridden per-organisation/sub-org once a multi-tenant/organisation concept exists in this app (it doesn't yet — see B2B portal in the roadmap's "What Remains"). The natural implementation is **not** an OOP-style abstract-class inheritance model — it's a priority lookup (check an org-scoped config row first, fall back to the global `app_config`/`feature_flags` row if none exists). Deferred until an organisation entity actually exists; building it blind now would be speculative.

#### Route Tab Bug Fixes & Per-Segment Visibility (Stages 25-26)

- **`is_visible` toggle** (`docs/supabase_migrations/stage25_trip_segment_visibility.sql`) — a boolean on `trip_segments`, defaulting `true`, toggled from `SegmentCard`. Purely a display flag: hides a leg from the Route tab's map without deleting it or affecting `order_index`/RLS.
- **`REPLICA IDENTITY FULL` fix** (`docs/supabase_migrations/stage26_trip_segments_replica_identity.sql`) — `route_geometry` is `jsonb` and a real routed path can easily exceed Postgres's ~2KB TOAST threshold, so it's often stored out-of-line. Under the default replica identity, Postgres's logical replication (what Supabase Realtime reads) omits *unchanged* TOASTed columns from an `UPDATE`'s WAL record — so a partial update like `{is_visible: ...}` broadcast a realtime row with `route_geometry` missing, which `tripSegmentsStreamProvider` then merged in, nulling the cached geometry until the next full re-fetch and reverting the map to a straight/curved fallback line. `REPLICA IDENTITY FULL` makes every WAL record carry every column's current value regardless of TOAST or which columns actually changed.
- Also fixed the same stage: delete no longer renumbers/re-upserts the rest of the route (the Route tab now sorts chronologically by departure/arrival time instead of the manual `order_index`, so delete is a single `DELETE` with no side effects on siblings), and an origin/destination swap button was added to the add/edit segment page.

#### Real Route Geometry via `lib/core/routing/` (Stage 24 — uncommitted as of 2026-08-09)

Caches a real routed road/footpath path on the segment row instead of always drawing a straight or curved-approximation line — see `route_curve.dart`'s curving logic above, which this supplements rather than replaces (non-routable modes, and any routable-mode leg with no cached geometry yet, still fall back to that).

- **Migration:** `docs/supabase_migrations/stage24_trip_segment_route_geometry.sql` adds `trip_segments.route_geometry jsonb` — nullable array of `[lat, lng]` pairs. Null means "not fetched yet" or "not a routable mode."
- **`lib/core/routing/routing_service.dart`** — `RoutingService` abstract interface (single method `route({origin, destination, mode})`, returning routed points or `null`), following this codebase's deliberate abstract-class+Impl+Provider convention for single-method services (see [[feedback-single-method-abstractions]] equivalent reasoning: don't collapse this to a bare function despite the `one_member_abstracts` lint). `isRoutableMode(TransportMode)` — only `car`/`motorcycle`/`bus`/`walk` route over a real network; `flight`/`ferry`/`train` keep the existing straight/curved line unconditionally.
- **Two implementations**, dispatched by `routing_service_provider.dart`'s `routingServiceProvider` the same way `RouteMapView` dispatches map engines — whichever `KumoMapProvider` is active decides which routing backend answers, so a segment's routed geometry always comes from the same ecosystem as the tiles it's drawn on:
  - `osrm_routing_service.dart` — free, keyless, hits the public OSRM demo router (`router.project-osrm.org`).
  - `google_directions_routing_service.dart` — uses `Environment.googleMapsApiKey`, a **separate** `--dart-define` value from the native Google Maps SDK key described above. The native key (Android's `google_maps_key` string resource / iOS's `Secrets.xcconfig`) is wired directly into the native map SDKs and unreachable from Dart; Directions API calls are made from Dart, so they need their own copy of the key, and the Directions API must be separately enabled for it in Google Cloud Console.
- **Composition point:** `lib/features/itinerary/presentation/providers/trip_segment_provider.dart`'s `FetchTripSegmentRouteGeometry` — deliberately at the presentation/provider layer, not a domain usecase, mirroring `ResolveAiSegments`'s existing cross-feature-composition precedent (domain usecases never reach into `lib/core/` directly).
- **Test coverage:** `test/core/routing/routing_service_test.dart`, `osrm_routing_service_test.dart`, `google_directions_routing_service_test.dart`, and `test/features/itinerary/presentation/providers/fetch_trip_segment_route_geometry_test.dart`.

#### Katha AI now produces route segments too (still dormant)

**Katha AI itself is not reachable in the running app** — both entry points (`create_itinerary_page.dart`, the "AI" button in `itinerary_detail_page.dart`'s Schedule header) still show a `"Katha AI coming soon ✨"` placeholder snackbar instead of calling `showAiGenerateSheet(...)`, per the Stage 13 gate (Edge Function undeployed, `ANTHROPIC_API_KEY` unset). This work makes the dormant pipeline itself segment-aware, so it's ready the moment that gate is lifted — the same "built but not wired up yet" pattern already used for the rest of AI generation.

- **`supabase/functions/generate-itinerary/index.ts`**: the prompt now asks Claude for a JSON **object** (`{ "items": [...], "segments": [...] }`) instead of a bare array. `segments` is only populated when the free-text `destination` field describes multiple stops travelled in sequence (e.g. "Munich, Bangkok, Chiang Mai, Pai") — one leg per consecutive stop pair, with a transport mode. `parseResponse` stays backward-compatible with the old bare-array shape (treated as `items` with no segments) in case the model ignores the object instruction.
- **Domain:** `AiGeneratedSegment` (mode + origin/destination **city names**, not yet geocoded) and `AiGenerationResult` (`items` + `segments`) replace the old bare `List<ItineraryItem>` return type through `AiGenerationRepository` → `GenerateItineraryUseCase`.
- **Data:** `AiGenerationDataSourceImpl.parseSegments` mirrors `parseItems`'s defensive style — an unknown `mode` falls back to `TransportMode.other`, a leg missing `origin` or `destination` is skipped rather than failing the whole response, unparseable times become `null`.
- **Presentation:** `ai_generate_sheet.dart`'s success view adds a "Route" preview list (mode icon + origin → destination) when segments are present; `showAiGenerateSheet` now returns the full `AiGenerationResult` on accept.
- **Resolving city names into real segments:** `lib/features/ai_generation/presentation/providers/ai_generation_provider.dart`'s `ResolveAiSegments` — geocodes each leg's origin/destination via the existing `NominatimGeocodingService` (same one the Route tab's location search uses) and inserts the resolved `TripSegment` via `AddTripSegmentUseCase`, renumbering consecutively and **skipping legs whose origin or destination can't be geocoded** rather than failing the whole batch. Lives at the presentation/provider layer (not a domain usecase) because it composes two other features' infrastructure — matches how this app does cross-feature composition elsewhere (e.g. `itinerary_detail_page.dart` wiring in chat/expense/packing/ratings providers directly), rather than introducing a first cross-feature domain-to-domain dependency.
- **Not wired up:** nothing currently calls `ResolveAiSegments` or the two placeholder AI entry points — that's the "wire up Katha AI's placeholder entry points" work explicitly deferred as a separate, larger task (it requires actually deploying the Edge Function and setting the Anthropic API key, both ops steps outside code changes).
