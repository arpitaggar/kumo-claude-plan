# lib/features/itinerary

Added 2026-08-15 (a docs/test audit pass found this file had never existed, despite `itinerary` being the app's largest and most-changed feature — every other actively-touched feature has one). Loads only when working under `lib/features/itinerary/`.

This is not an exhaustive API reference for all 67 files here — `travel_itinerary.dart`/`ItineraryModel`/the standard Clean Architecture usecase-per-operation layering are self-explanatory from the code and this project's root `CLAUDE.md`. What follows is the "why," for the pieces that aren't obvious from reading the code alone.

### Trip export/import file (`domain/entities/trip_file.dart`, `domain/usecases/import_trip_file_usecase.dart`)

A standalone, versioned JSON format (`kumo_trip_file_version`) a user can export from the detail page's app bar and hand to someone else (AirDrop/email/message) to get their own independent copy of the trip.

- **Deliberately not a dump of `ItineraryModel`/`TripSegmentModel`'s backend-row JSON.** Reuses the boundary `ForkPostUseCase`/`ItineraryPost` already draws for "clone this trip into a different account": title, dates, theme, currency, items, and route segments only — never members, expenses, or notes, since those either name other real people or carry financial data that isn't the exporting user's alone to hand out. Using a hand-written shape rather than the model's own JSON means a future Supabase schema change can't silently break an old export file sitting in someone's inbox; `TripFile.fromJson` throws a user-facing `FormatException` on a missing/invalid version marker or a version newer than this app supports, rather than a cryptic type-cast crash.
- **`TripFileSegment` deliberately drops `TripSegment.id`/`itineraryId`** (fresh ones are assigned on import — the original ids never needed to travel, they're only unique within one itinerary's own embedded list) **and `routeGeometry`** (cheap to re-fetch from the routing service on import, same as adding a segment by hand — not worth the file size for a long route).
- `ImportTripFileUseCase` is the file-based counterpart to `ForkPostUseCase`: composes the existing `CreateItineraryUseCase` + `AddTripSegmentUseCase` (one call per segment, so ordering/validation matches a user adding them by hand) rather than writing a new persistence path.

### GPS coordinate / `.gpx` import (`presentation/widgets/location_search_sheet.dart`, `lib/core/geocoding/gpx_parser.dart`)

`LocationSearchSheet` (used by `add_edit_trip_segment_page.dart` for both origin and destination) has three tabs — Search (live Nominatim), Coordinates, and Import GPX — and all three produce the same `GeocodingResult{name, lat, lng}` shape, so nothing downstream of the sheet (`Waypoint`, `TripSegment`, every existing usecase) needed to change.

- `gpx_parser.dart`'s `parseGpxWaypoints` prefers `<wpt>` waypoints (what most GPS apps export for points of interest); if a file has none, falls back to `<rte>` route points, then to just the first/last point of each `<trk>` track segment — enough to pick a *single* location, which is all a segment endpoint needs. Throws `GpxParseException` (not a generic error) so the UI can show "this doesn't look like a GPX file" vs. "no usable points found" as distinct messages.
- The Coordinates tab's free-text parser (`_parseCoordinates` in `location_search_sheet.dart`) accepts both `"lat, lng"` and `"lat lng"` and validates the range (±90/±180) before ever constructing a result — same validation Bounds `gpx_parser.dart`'s `_pointFromElement` also applies to every parsed point, so a malformed coordinate can't reach the map from either input path.
- **Not tested here:** the "Choose .gpx file" button's real `file_picker` invocation — no test double exists for that platform channel anywhere in this codebase (same gap as `ImagePicker` in `chat_page.dart`'s attach sheet). `test/features/itinerary/presentation/widgets/location_search_sheet_test.dart` covers everything else (Search results/error/clear, Coordinates valid/invalid/range/clear-on-retype, the GPX tab's pre-pick empty state) through mockable seams.

### Editable dates (draft only) and theme (any time) — `presentation/pages/itinerary_detail_page.dart`

- **Start/End dates are only tappable while `ItineraryStatusEnum.draft`.** Once a trip leaves draft, other members may already be relying on the dates (route segments, expense periods, notifications), so changing them silently underneath a shared trip isn't safe to allow inline — see `_pickDate`'s comment. Picking a new Start auto-advances End if it would otherwise precede it (same clamp logic as trip creation); picking an End before Start is rejected with a snackbar.
- **Theme, by contrast, is editable regardless of status** (`_changeTheme`) — it's cosmetic, not something other members build state on top of.
- **A trip's `Theme` override never blends with the app-wide `KumoTheme`.** `ColorScheme.fromSeed(seedColor: tripTheme.primary)` derives a complete, accessible scheme from the trip's one hand-picked accent color, wrapped around the whole detail page — every tab that reads `context.colorScheme` picks it up automatically, and it stays fixed regardless of whether the ambient app theme (e.g. a dark theme like Synthwave Tokyo) is light or dark. This wasn't always true: an earlier version (`TripThemeContextX.withContext()`, since deleted) tried to reconcile the trip theme with the active app `ColorScheme`, which only worked for the `classic` preset and produced a visibly broken mixed look for every destination-styled theme under a dark app theme — see `docs/Checklist.md`'s 2026-08-15 "Trip theme bugs" entry for the full incident. Dialogs/sheets opened from within the page (delete confirmation, date picker, the theme picker itself) are inserted at the Navigator/Overlay level and correctly fall *outside* this override, staying on the app's own theme — the right split, since those are system-level interactions, not trip content.
- **`ItineraryListNotifier.updateItinerary()`** exists specifically so Home/Trips cards reflect an edit immediately. `itineraryListProvider` is a plain fetched snapshot, not a live stream — every mutation from the detail page used to call `updateItineraryUseCaseProvider` directly, updating the backend row but never touching that cached list, so cards silently showed stale data (theme, dates, status, everything) until an unrelated refresh happened to re-fetch. `updateItinerary()` patches the matching item into the cached list on success and is silent on failure (matching `softRefresh`'s convention — a failed single-field edit shouldn't blow away an otherwise-good list into an error state), returning the same `Either` the usecase does so every call site's existing error handling is unchanged. All 9 direct `updateItineraryUseCaseProvider` call sites in `itinerary_detail_page.dart` route through it.

### Stay tab and `accommodationSources` (`presentation/pages/itinerary_detail_page.dart`)

Multi-source accommodation search, added the same day as the theme/dates work above and following the exact same editable-any-time pattern (`_changeAccommodationSources`, a bottom sheet, `updateItinerary()`). The actual source abstraction, mock implementations, and aggregation logic live in `lib/core/accommodation/` (see that folder's own CLAUDE.md for the full design rationale — why every source is mocked right now, why cross-source listings aren't merged, how to wire up a real source later) — this page only owns the tab UI and the trip-level `accommodationSources` setting.

- **`TravelItinerary.accommodationSources`** is always a concrete list (never null), unlike `UserProfile.enabledAccommodationSources` (null = "all sources"). It's resolved from the creator's profile default *once*, at trip-creation time (`create_itinerary_page.dart`'s `_submit()`, mirroring how `themeKey` already gets defaulted there) — deliberately so a trip's setting doesn't silently change later just because the profile default changes or a new source ships.
- **The Stay tab's search center comes from geocoding the trip's own title** — itineraries have no dedicated destination-coordinates field. A trip titled without a recognizable place name won't resolve to anywhere useful; there's no manual "pick a different center" fallback yet.
- **Found via the Stay tab's own tests, not code review:** the listing card's price/"View on `<source>`" row overflowed at phone width (430px) because neither child was flex-wrapped — a long source name like "Hostelworld" combined with the price text was wider than the card. Same failure class as the 2026-08-13 overview-pill overflow on this same page — narrow-viewport bugs that the default (wide) `flutter_test` surface can't catch, only a test that explicitly sets a phone-sized `tester.view.physicalSize` can.

### Member-row long-press menu (2026-08-16)

`_MemberRow`'s old tap-triggered three-dot `PopupMenuButton` (role change / remove) was replaced with a long-press-triggered bottom sheet (`_MemberActionsSheet`) that also offers "Message privately" — see `lib/features/direct_messages/CLAUDE.md` for the DM feature itself. `_MembersCard._changeRole`/`_removeMember` are unchanged, just now invoked from the sheet instead of the popup menu. One consistent interaction per row instead of two overlapping ones (a tap-icon and, separately, whatever a future long-press might have added) — "Message privately" is hidden on your own row (`onMessage` is `null` there), and the manage rows stay gated on the same `canManage` the old menu used.
